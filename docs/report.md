# 第五组日志监控项目报告

GitHub：https://github.com/EchO-NN/group5-log-monitor

## 一 任务与方案

我在第五组攻防演练中负责日志监控，主要工作是把分散在各台虚拟机上的安全事件集中到 Wazuh，再将需要调查的告警交给 IRIS 管理。在平台基础配置之外，我完成了告警筛选与聚合、独立案件创建、远程日志查询、AI 调查工具和性能数据关联程序。演练开始时创建案件，结束后启动调查，最后在同一个 Case 中查看事件总结、时间线、任务、资产、笔记和证据。

这部分工作的核心，是让一次操作能够从现象追溯到具体记录。例如，业务接口报错只能说明服务出现问题；继续查看应用日志，可以定位到哪张表访问失败；再核对数据库日志，才知道错误发生前出现了什么结构变更。备份文件也是同样的道理：文件完整性告警指出对象发生变化，认证日志说明访问来源，审计日志进一步给出执行身份、系统调用和文件路径。监控平台需要把这些记录放在一起，才能解释事件经过。

本项目采用 Wazuh 4.14.9 和 DFIR-IRIS 2.4.29。Wazuh 承担日志接收、解析和规则匹配，IRIS 承担案件管理，外部调查程序负责模型调用、工具执行和进度保存。新增的 VM9 性能模块读取 Prometheus 历史指标，使调查能够同时查看安全行为、主机资源变化和业务状态。三个来源使用各自的时间戳，再按主机和事件对象关联。

在 Case 2 的实际演练中，监控记录覆盖了员工终端登录、应用主机访问、高权限执行、备份账号认证、归档删除、数据库表重命名及业务探测失败。调查结果组织为 14 个时间线节点和 12 条关系，并保存了对应的查询证据。报告后半部分以这次案件为例，说明各项配置如何用于实际判断。

VM8 是日志监控与案件管理节点。A 电脑负责运行远程采集调度和 AI 调查进程，通过管理通道访问各台虚拟机。VM9 集中提供性能指标和业务探测结果。这样安排后，IRIS 的页面操作、Wazuh 的日志检索与模型调查可以分别执行，长时间分析也有独立的状态记录。

### 个人实现内容

我先完成日志接入和规则配置，确定不同主机需要保存哪些信息，再处理告警数量过多的问题。Wazuh 中适合检索原始事件，IRIS 中则需要把同类事件合并成可以阅读和跟踪的调查条目。因此，我在两者之间加入了固定策略的转发程序，保留原始等级、成员记录和来源摘要。

随后，我把每轮演练整理为独立 Case，并加入结束后的工具调用式调查。模型可以根据线索提出任务、查询主机和阅读已存证据，执行器负责完成实际操作。VM9 扩展沿用同一套证据接口，把性能样本交给调查工具查询。源码构建、测试用例、部署模板和报告均放在独立项目中，便于复现和课堂展示。

## 二 日志采集与 Wazuh 检测

### 采集内容及其用途

认证日志主要回答“哪个账号从哪里登录”。SSH 记录中保存来源地址、端口、认证方式和会话信息，sudo 记录则用于观察账号调用高权限命令的行为。这些信息在跨主机调查中很重要：VM5 记录的来源如果是 VM3 的地址，就可以把员工终端和应用服务的活动放在相邻的调查范围内。

Auditd 补充了认证日志之后的执行细节。我关注原始登录身份 auid、执行时的 uid 和 euid、进程及父进程编号、可执行文件、系统调用、返回结果和目标路径。以文件删除为例，成功的 unlink 调用能够把一次操作与具体文件绑定；以权限变化为例，auid 保留登录账号上下文，uid 和 euid 反映该次执行所使用的权限。两组身份字段一起看，比只看命令名称更有用。

文件完整性监控记录文件新增、修改、删除以及哈希、大小等属性变化。VM7 的备份目录是重点对象，VM5 的应用配置与实验 sudoers 路径也进入关注范围。文件变化还需要结合操作发生的时点解释：文件刚创建时可能尚在写入，后续清单和哈希校验用于确认查询时的完整状态。

网关日志用于观察连接是否经过访问控制。数据库日志记录 SQL 及对象变化，应用日志记录具体业务错误，VM9 业务探测从独立节点检查接口结果。软件清单、漏洞匹配和配置检查则帮助了解主机状态。实际案件分析以事件发生时的认证、执行、文件和业务记录为主，各类状态信息用于补充调查上下文。

### 自定义规则的设置

项目增加了网关拒绝和备份校验失败两条规则。规则编号是配置中的唯一标识，等级也是规则配置的一部分；它们决定日志命中后怎样进入告警流程。

| 规则 | 等级 | 匹配条件 | 记录含义 |
| --- | --- | --- | --- |
| 100510 | 7 | 日志包含 VM2-ACL DROP | 网关访问控制拒绝了该连接 |
| 100511 | 12 | 程序为 backup-integrity-check，包含 status=FAILED | 备份完整性检查报告失败 |

100510 的配置较直接：从网关送来的日志中匹配拒绝标记，并为该事件生成 7 级告警。课堂展示时可以打开原始记录，展示来源、目标和端口，再说明该连接已经被访问控制拦截。100511 面向备份业务，检查失败会影响备份文件的可用性，因此配置了更高的等级。

```xml
<rule id="100510" level="7">
  <match>VM2-ACL DROP</match>
  <description>Group5: VM2 ACL rejected traffic</description>
</rule>
```

### 告警筛选与低等级白名单

IRIS 的主要接收阈值是 Wazuh 原始等级不低于 7。与此同时，策略为关键账号和路径保留了少量低等级事件。原因来自实际调查：成功登录通常不是高等级风险，但备份删除之前的 bk_operator 登录恰好是定位访问来源的重要记录。如果只按高等级筛选，能看到文件消失，却容易丢掉此前的会话信息。

白名单账号包括 dev_zhang、app_ops、bk_operator 和 db_admin。认证规则覆盖 5715、5716、5710、5503、5557、2501，sudo 规则包括 5401 至 5403；文件新增规则 554 结合 /lab_backup/、应用配置及实验 sudoers 等路径使用。程序执行还单独处理 92601，并检查登录身份字段。白名单按规则和对象共同限制，避免把所有普通登录和文件变化都转成独立 Alert。

Wazuh 原始 level 随成员记录保存，IRIS 的严重性由固定映射计算：等级 7 至 11 映射为 4，12 至 14 映射为 5，15 及以上映射为 6，选中的低等级记录映射为 3。这样既保留检测规则给出的原始信息，也让 IRIS 使用统一的展示等级。转发阶段只描述发生了什么，攻击性质和事件间联系留到调查时结合证据判断。

### 聚合与原始证据保存

同一轮演练中，程序根据主机、规则、关键解码字段和固定五分钟时间桶生成分组键。匹配的事件合并展示，记录数量、首次时间、末次时间和成员明细。五分钟时间桶是固定区间，因此跨桶事件会分别展示；不同 run 的记录也有独立分组，上一轮事件不会混进新案件。

这种方式解决了短时间内重复告警占满页面的问题。例如，同一类应用错误持续出现时，IRIS 可以显示一个含多条成员记录的条目，调查时仍能展开查看时间分布。展示数量减少，原始事件和每条记录的等级继续保留。普通采样及未进入 Alert 的记录存入证据区，后续查询仍能使用。

转发程序使用 SQLite 保存接收记录、分组、投递状态、案件归属和重试信息，原始正文按内容摘要归档。展示字段经过筛选，只保留账号、地址、程序、系统调用和文件摘要等有用信息；执行器在保存和输出时对凭据内容进行脱敏。投递重试先核对已保存状态，案件写入也核对已有对象，减少网络重连造成的重复内容。

## 三 一轮演练的案件处理

### 从 begin 建立独立案件

监控程序将一次演练称为一个 run。run 保存采集与分析范围，IRIS Case 保存这一轮的展示内容，两者保持对应。操作人员在攻击开始前执行 begin，传入便于识别的标签，程序创建 Case 并记录开始时间。

```bash
./监控自动化.sh begin --label "第五组正式演练"
./监控自动化.sh status
```

begin 使用独立请求编号。如果连接中断，客户端保存这次请求意图，重试继续使用同一编号；收到成功回执后再清除本地待确认记录。这样可以处理“远端已经创建案件，本机还没收到回应”的情况。每轮的 Case 编号由 IRIS 分配，标签用于说明演练名称，程序内部通过 run 标识关联日志与查询结果。

演练过程中，采集器持续读取主机日志，Wazuh 生成规则告警，转发器把筛选后的事件写入本轮案件。status 展示当前 run、队列状态和 Case 信息。队列中的 sent 表示已投递，evidence_only 表示保存为证据；这两个数量分别反映展示数据和证据存储，不能简单相加当作攻击次数。

### finish 后的日志收尾与调查

```bash
./监控自动化.sh finish
watch -n 2 './监控自动化.sh ai'
```

finish 记录演练结束时间，然后等待在途日志进入队列。配置中的稳定等待为 60 秒，排空等待为 300 秒，用于处理日志采集、网络传输和告警生成之间的时间差。分析窗口按本轮开始和结束时间确定，查询时可以向前后扩展 120 秒，用来读取认证前后和操作后的相关记录。

运行状态 finished 表示本轮记录已经结束，AI 作业还有自己的执行状态。pending 是等待领取或等待重试，running 是正在执行，done 是调查结束。将两组状态分开，操作人员就能知道当前是在收尾日志、等待模型，还是已经完成案件整理。流式返回会刷新空闲计时，进度页面显示最近动作、工具和任务状态。

远程采集器还保存每台主机的读取游标。数据成功送达 VM8 后才推进游标，某一台主机连接异常时保留原位置，其他主机继续处理。下次连接成功后，采集器从上次确认的位置继续读取。案件范围、主机游标和模型作业各自保存，使一个环节的重试不会重置整个演练过程。

## 四 IRIS AI 调查的实现

### 模型与执行器如何配合

我在 IRIS API 和主机查询程序上封装了一组函数调用工具。课堂环境通过 PackyAPI 调用 gpt-6.1-sol，推理强度配置为 xhigh。模型负责选择下一项调查动作，执行器读取日志、调用 IRIS 或整理结果，再把实际返回内容交给模型。一次调查由多次查询和写入组成，每一步都有保存位置和执行回执。

调查开始时，模型得到本轮告警、时间范围、主机角色和证据目录。主机角色帮助它判断应当查询哪台机器，例如数据库对象变更对应 VM6，备份清单对应 VM7。预设的攻击十阶段没有放入这轮判断输入，时间线由收到的事件和实际查询结果组织。项目脚本和历史内容可以作为调查线索，当轮发生的行为由本轮记录支撑。

### 先提出任务再读取证据

模型首先建立调查任务，将笼统的告警转成能够通过日志回答的问题。例如，看到备份删除告警后，任务可以写为“核对删除前的访问来源、登录账号及文件操作”；看到业务错误，则可以围绕“错误涉及哪些数据库对象，之前是否发生结构变化”展开。任务确定后，后续查询和证据都归到相应问题下。

| 调查工具 | 实际操作 |
| --- | --- |
| create_tasks 与 update_task | 创建调查问题，记录核查进展和结果 |
| read_evidence | 阅读原始告警及前序查询证据 |
| query_host | 查询认证、审计、服务日志和备份清单 |
| inspect_files | 查看目录、元数据，分页读文本或搜索内容 |
| query_collected | 查询已归档的数据库、应用、业务和性能数据 |
| record_case | 分次写入案件各区域 |
| finish_case | 核对调查状态与证据覆盖后结束作业 |

例如，备份任务会先读取 VM7 的认证信息，找到 bk_operator 从哪个地址登录，再检查该时间段内的审计记录。审计结果如果出现成功 unlink，模型就可以继续核对文件路径、UID 和进程关系。数据库任务则从结构变更开始，将对象名称与 VM5 应用错误、VM9 业务探测相互对照。工具选择直接围绕当前问题展开。

任务完成有程序条件。被标为 completed 的任务至少要引用一次属于该任务且执行成功的实际查询；审计存在续页时还要继续读取或明确记录查询状态。这里的“完成”表示已经完成相应调查动作。修复业务、恢复文件等处置操作作为事件内容另行记录，避免把查询完成和系统恢复混为一个状态。

### 分页读取与执行回执

审计查询以留存快照为范围，每页返回最多 80 条记录，通过游标继续读取。游标绑定查询窗口、筛选条件和日志文件状态，可以处理轮转日志及 gzip 文件。在 Case 2 中，VM5 的主审计查询读取了 74 页、5609 条记录，VM7 读取了 8 页、419 条记录，分页让较大的日志量可以逐步交给模型分析。

执行器收到工具调用请求后，先保存调用信息，再读取日志。返回结果包含主机、查询类型、时间范围、采集时间、记录数量和正文。程序核对这些字段后生成证据编号，将内容摘要、任务归属和查询回执保存下来。相同步骤及相同调用摘要再次提交时，程序可以返回已有回执，避免重试重复执行。

模型的进度由执行记录体现。页面展示当前工具、简短操作目的、已有任务和最近实际动作；长查询或模型返回期间，心跳与空闲计时继续更新。这样课堂展示时可以看到它正在查哪台主机、围绕哪个问题工作，以及哪些证据已经保存，而不是只等最终的一大段正文。

### 结论怎样追溯到原始记录

原始告警使用 A 编号，实际查询结果使用 E 编号。时间线节点引用这些编号，证据区域再保存相应摘录或附件。阅读者可以从 Summary 中的判断进入 Timeline，找到该事件引用的 E 证据，再查看查询返回的原始日志。这种组织方式使一句结论有明确的核对入口。

时间线节点除时间和描述外，还包含前置节点、关系类别和关联依据。关系分为因果、提供后续条件、活动延续和时间相邻，并记录确认事实与分析推断。例如，同一文件路径的删除与重新创建属于对象活动的延续；表重命名后应用对同名表报错，能够使用对象一致性说明故障关系；同一时间段的两条独立记录则保留为时间相邻。

写入前，程序检查引用是否存在、节点时间是否落在引用证据范围内、前置节点是否晚于后续节点，以及关系是否形成循环。结束案件时，还会核对任务状态、活动查询和证据覆盖。IRIS 中被人工修改过的内容有冲突检查，自动调查根据已保存版本写入。模型提出文字判断，执行器负责保证记录结构、引用和实际操作能够对应。

### 案件各区域如何使用

Summary 用于概括攻击行为、手段、涉及资产和造成的影响，正文围绕本轮最重要的事件展开。Timeline 按事件时间还原过程，说明各环节怎样衔接。Tasks 保存调查问题和核查结果，便于查看哪些结论已经经过查询。

Notes 保存查询中形成的判断依据和过程说明，Assets 描述相关主机在事件中的作用，Evidence 将原始告警与查询材料按主题组织。Case 2 最终保存了 3 个任务、5 项资产、3 条笔记和 4 组证据。几个区域互相引用，课堂展示时可以先读 Summary，再从时间线选取一个节点追到证据，而不必逐条翻阅所有原始日志。

## 五 VM9 性能数据联合分析

### 指标读取与标准化

VM9 扩展使用 Prometheus 的 query_range 接口读取历史时间序列。采集器按 30 秒步长请求，单次最多回看两小时，将响应转换为统一的性能样本，再交给 VM8 保存。CPU、磁盘吞吐与网络吞吐采用两分钟计算窗口，便于把持续资源变化放到安全事件附近观察。

| 指标字段 | 数据含义 | 调查用途 |
| --- | --- | --- |
| cpu_percent | CPU 使用率 | 观察命令执行附近的计算负载 |
| memory_percent | 内存使用率 | 查看进程和应用的内存压力 |
| load1 | 一分钟负载 | 观察系统排队与负载变化 |
| disk_used_percent | 磁盘空间使用率 | 观察文件增长及容量压力 |
| disk_read_bytes_per_second | 磁盘读取速率 | 对照数据库读取和归档操作 |
| disk_write_bytes_per_second | 磁盘写入速率 | 对照备份写入和数据修改 |
| network_rx_bytes_per_second | 网络接收速率 | 观察接收方向的流量变化 |
| network_tx_bytes_per_second | 网络发送速率 | 观察发送方向的流量变化 |
| target_up | Prometheus 抓取状态 | 说明目标在采样时是否可达 |

样本分别保存 sensor_host 和 target_host。sensor_host 表示从 VM9 采集，target_host 表示这条曲线实际对应哪台机器。TARGETS 映射将实例地址关联到 VM2 至 VM9，指标集中存放在 VM9，VM5 的 CPU 曲线仍属于 VM5，应与该主机的认证和执行日志关联。

标准化时检查指标名称、实例、时间和数值。未知实例、NaN、无限值、负数、不合法百分比和窗口外数据会被排除；无样本与查询失败各有独立状态。重复采集使用稳定标识去重。指标值、单位、时间、实例和来源摘要一起保存，后续统计能够追溯到具体采样。

### 按主机与时间查询

performance_metrics 按目标主机和指标统计样本数量、最小值、最大值、平均值、峰值时间以及末次值。统计在限制展示条数之前执行，查询范围内第 80 条之后的样本也能影响结果。数据量达到扫描或输出边界时，结果会附带 truncated 标记，调用方可以据此调整后续读取范围。

performance_correlations 读取符合告警策略的 Wazuh 事件，寻找同一目标主机在事件前后 120 秒内的性能样本。返回内容包含事件编号、事件时间、目标主机和附近的指标摘要。它首先提供可核对的时间联系，模型再结合账号、进程、文件和业务记录解释这段资源变化。

例如，调查 VM5 的 sudo 活动时，可以先查询附近的 CPU 和磁盘写入情况；发现资源变化后，再读取同一窗口中的程序执行与应用日志。调查数据库故障时，则可以同时对照 VM6 指标、VM5 应用错误和 VM9 业务探测。这样的查询顺序把性能指标用作补充线索，最终事件描述仍引用实际行为和业务结果。

### 业务探测与本地验证

业务探测采集同时保存成功和失败，并记录 HTTP 状态与耗时。持续保存正常结果后，调查可以查看故障前后的状态变化，也可以观察业务重新返回成功的采样时点。性能曲线、业务结果和安全日志保留不同来源，按时间放在同一调查窗口内阅读。

本次扩展完成了响应解析、样本标准化、证据入库、指标汇总、事件关联和 Agent 工具路由的本地验证。测试覆盖无响应、空结果、未知实例、非法数值、窗口外样本、重复样本以及跨轮隔离。专门的汇总用例将峰值放在第 80 条之后，检查统计结果是否包含后续样本；主机匹配用例检查 VM5 的告警不会关联到其他虚拟机的曲线。历史 Case 2 使用的 VM9 证据是业务探测记录，新增性能接口作为项目功能单独验证。

### 从登录路径定位备份操作

03:26:48，VM3 接受 dev_zhang 登录。随后 VM5 的认证记录出现来自 192.168.33.15 的 app_ops 会话，该地址对应 VM3。03:27:40.606，VM7 又接受来自 192.168.31.30 的 bk_operator 公钥认证，该地址对应 VM5；03:27:41.104 启动 internal-sftp。从各主机分别记录的来源和账号，可以整理出员工终端、应用服务到备份服务的访问路径。

备份删除的直接证据来自 VM7 审计事件 43543。记录中的 syscall 为 87，对应 unlink，执行结果为成功；uid、euid、auid 均为 1001，目标是 /lab_backup/star_web_v2.3_stable.tar.gz。删除进程编号为 157202，父进程为 157201，关联查询中还保留了该时段的 sshd 凭据上下文。文件对象和成功返回值共同确认了这次删除操作。

认证与 SFTP 会话为删除前的访问条件提供了依据，文件完整性告警和审计则从两个角度记录了同一目标的变化。随后备份完整性检查出现 FAILED 和 file_unreadable。案件将这些信息放在同一备份主题中，分别说明访问、执行和检查结果，避免把多个采集渠道捕获的相近消息重复算成多次破坏。

03:28:55，同名文件出现新增记录，审计记录了成功 openat。创建瞬间的文件大小为零字节，后续 06:06:43 的备份清单显示归档为 1861 字节，SHA-256 与基线及删除前记录一致。时间线分别保存“重新创建”和“后续字节完整性核验”两个节点，使删除、重建和校验的时间关系清楚可见。

### 数据库操作怎样影响业务

03:27:45.519，VM6 保存了对 lab_orders 和 lab_tickets 的重命名语句，目标对象带有 rehearsal_hold 时间标记。03:27:47.126，VM5 开始对 lab_business.lab_orders 报告 1146 和 table_not_found；稍后 lab_tickets 也出现同类错误。数据库中的对象名称与应用报错逐一对应，结构变更之后的实际影响由应用日志给出了独立记录。

03:28:13，VM9 对 orders 和 tickets 的探测均返回失败。此时 VM5 仍在记录相关表访问错误。数据库结构变更、应用对象错误和业务探测结果围绕同一组业务相互印证，因此案件 Summary 将其概括为对订单和工单业务可用性的破坏。

03:28:45.819，数据库日志收到两张业务表的反向重命名语句，语句中的目标名称为原来的表名。这一节点与前序变更使用同一组完整对象名称，在时间线上形成对象层面的回退活动。业务失败记录用于说明故障影响，反向语句用于记录后续数据库操作，各自按照原始时间进入案件。

### 高权限执行的记录方式

VM5 的审计记录中，sudo 子进程执行了 /usr/bin/id，auid 为 1001，uid 和 euid 为 0。这里保留登录身份和执行身份，能够清楚说明普通账号上下文中出现了 root 权限执行。案件以这一实际结果组织时间线，再将前面的 app_ops 登录作为相关访问条件进行分析。

03:28:31 之后还出现临时目录脚本及 sudo、dash 执行上下文。它们发生在备份删除和数据库表变更之后，因此时间线将其放在后续执行分支中。事件排列遵循日志时间，关系说明再使用身份、进程和对象等字段。这样读者能区分哪些环节是直接记录，哪些联系来自跨记录分析。

从监控结果看，这轮演练呈现了账号访问、应用主机高权限执行、备份归档删除和数据库业务对象修改等行为，备份检查与独立业务探测进一步记录了影响。IRIS 将它们组织到同一个案件中，Summary 说明事件性质，Timeline 展示过程，Evidence 保留可回查的依据。课堂展示时，选择备份删除或数据库故障任意一条主线，都能从结论追到具体日志。

## 九 项目体会

这次工作中，重复告警最先影响了阅读，而一些低等级登录和文件新增又是重要线索。我将展示筛选、聚合和原始证据保存分开处理，使页面保持可读，也能继续追查前后操作。

AI 调查部分让我把查询、证据和案件写入连接起来。模型围绕问题调用工具，执行器保存返回结果并检查引用，IRIS 展示经过核查的记录。性能模块再补充主机负载和业务状态。这些实现使我能够在展示结论时打开对应日志，说明判断来自哪台机器、哪次操作和哪个时间点。
